File I/O tools User Guide

File I/O helper functions API File I/O tools API and User Guide File I/O tools User Guide.

1. Introduction

RSDK debug support and File IO features are provided directly by source code and Lauterbach T32 scripts found in /Tools/Debug_tools folder For Lauterbach T32, rsdk creates a custom semihosting mechanism, based on setting and intercepting breakpoints in the application code.

File I/O operations can be done in the user app by invoking DbgReadFile(), DbgWriteFile() and DbgPrintMsg().

Lauterbach T32 is the default tool used for debugging and transferring data between the RSDK applications running on S32R platform and the user's PC.

2. Environment Dependencies

The tools and dependencies used for building and executing the RSDK modules are listed in RSDK Environment Dependencies section.

3. Integration and Execution

To enable file IO functionality and full debug support, source code from /Tools/Debug_tools must be included in the user application and Lauterbach T32 scripts in /Tools/Debug_tools/T32 must be used to execute it.

3.1 Lauterbach support

All calls to file IO functions are tightly coupled with the set of script files (.cmm) that are included in RSDK package, by making use of breakpoints.
An effect of this is that, in multicore applications, calls to functions like DbgPrintMsg() are visible from only one of the cores, at a time.
See File IO API description for details.

3.5 Preprocessor defines

The debug messages output and file I/O method are selected at compile time for each executable application, by a set of preprocessor macros.

Only the basic file IO and debug mechanisms are supported, using Lauterbach Trace32 debugger. TFTP, UART and inter-core messaging protocols are not implemented.

Attention
Applications using these source files and scripts must ensure that none of the following macros are defined: STDIO, TFTP_CLIENT_EN, PROXY_CLIENT_FILEIO, PROXY_SERVER_FILEIO, UART_ENABLED, PE_SEMIHOSTING_EN.

Status and Error Reporting

Unified error reporting and handling mechanism for all RSDK modules errors All RSDK modules' API functions use the same enumerated typedef for returning error and status: rsdkStatus_t. The enumeration allocates different numeric intervals for each RSDK module and for the user app, such that there is no overlap between them.

Trace Log User Guide

Simple, platform-independent trace logging mechanism.

1. Introduction

The RSDK Trace module provides a simple, lightweight, platform-independent trace logging mechanism for application-level debug and monitoring. It relies on hardware features which are usually found in all embedded multicore platforms: hardware timers and shared memory access.

2. Module description

The trace module consists of 2 components:

  • Trace Logger : a library containing the trace logging mechanism. It uses an internal circular buffer to hold information and exposes 3 API calls, RsdkTraceInit(), RsdkTraceLogEvent(), RsdkTraceDump(), that can be used in any RSDK application/driver in order to obtain information.
  • Trace Parser : a PC-based Matlab application which parses the binary trace data produced by the Trace Logger and produces a human-readable *.xls output
Figure 1: Trace module architecture and deployment

3. Dependencies

Although the Trace Logger is designed to be platform-independent, the Trace module is built and tested in this context using the RSDK Environment Dependencies.

Note
Debugger support is included here for File IO operations (trace dump to PC). However, the File IO method is not programmed in the Trace Logger, but provided by the user application as a callback. Therefore, it can be replaced by any other 3rd party function which makes use of other communication mechanisms without breaking functionality.

4. Trace Software Components

The RSDK package includes the following items which implement the functionality of the Trace module:

  • /Tools/Trace/api/trace.h : Header file containing Trace Logger API definition.
  • /Tools/Trace/bin/librsdk_trace_< os >_< compiler >_< platform >_< core >.a : Trace Logger library built for a specific execution environment. No debug symbols.
  • /Tools/Trace_parser/* : Matlab source files for the Trace Parser.

5. Build and Execution

5.1 Using the Trace Logger

The Trace Logger can be used to register runtime events from an application. By running it on a S32R embedded platform, it will produce a binary trace file (.hex) with the recorded data. Events can be logged directly from the application, but, also, from any other driver used by it. The application and each driver that registers events must be linked with the trace library.

Some RSDK drivers and applications are instrumented to allow tracing. The trace can be enabled/disabled by defining/removing TRACE_ENABLE. This macro must be set by all the components that log events. E.g. Defining TRACE_ENABLE only at the application level will allow only application specific events to be recorded. To also register events from a driver (e.g. SPT), TRACE_ENABLE must also be defined when building the corresponding driver.

Attention
Only the application should initialize the Trace Logger and dump the captured data. Drivers should never perform these actions.

5.2 Using the Trace Parser

The RSDK Trace Parser is a Matlab script. It reads and parses the trace binary file created by the CPU during RSDK application runtime. It gives the parsed content as output, in a cell array, and also writes it to a xlsx file located in the same path as the input binary file.

Attention
There is a known limitation in the Trace Parser. Since the Trace Logger uses 32-bit timestamps, applications with a long enough execution time will cause the timestamp counter to wraparound one or multiple times. The Trace Parser can detect such a wraparound, adjust the timestamps accordingly and compute the time elapsed between events, but if between the registration of 2 consecutive events there is a large enough time gap (causing more than one wraparound), the Trace Parser will not be able to interpret it correctly.

The way the input is interpreted (e.g. timer frequency used at runtime) and the way the output is displayed (e.g. xlsx file, plots) can be controlled using a configuration file.

The RSDK Trace Parser can display 2 figures:

  • A timeline with all jobs (as intervals) and debug events (as individual timestamps) encountered. This figure can be adjusted to display details about any part of the execution by using the dedicated buttons implemented and the zoom and pan utilities located in the default Matlab figure toolbar.
Figure 3: Trace Parser Timeline Figure
  • A statistic overview of the execution. This figure has a pie chart that represents the entire application execution and some tables which give additional information about the recorded events as a statistic.
Figure 4: Trace Parser Stats Figure

In order to use this tool you need to have Matlab installed (preferably 2012a or more recent).

The Trace Parser source code is directly executable in Matlab. Steps to run the Parser:

  • Set the wanted configuration in the dedicated file (< rsdk_path >/Tools/Trace_parser/platform_config.ini).
  • Open Matlab and set the working directory to < rsdk_path >/Tools/Trace_parser/src/.
  • Call RsdkTraceParser('< relative_path >/< trace_file_name >', '< relative_path >/< app_header_name >').
Note
The path to the application header file is required in order to decode application specific trace events. This header must contain these custom trace events. If there are no such events defined, this path can be omitted. E.g. If the events are recorded only from a RSDK driver, RsdkTraceParser('< relative_path >/< trace_file_name >', '') is a valid call.
